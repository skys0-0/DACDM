# S1.3.7 — LeetCode Weekly Contest Hard Metadata Candidate Freeze

**Status:** IMPLEMENTED / FREEZE WORKFLOW PENDING  
**Scope:** Metadata candidate construction only  
**Confirmatory admission:** NOT YET PERMITTED  
**Paid inference:** PROHIBITED

## Purpose

S1.3.7 constructs a deterministic candidate universe for the Pilot 01 LeetCode Weekly Contest Hard task source before any paid inference. It exists because the frozen protocol requires timestamp-filtered LeetCode Weekly Contest tasks and IF-02 requires stable canonical task identifiers, Hard classification, contamination eligibility, and an executable oracle.

This stage does **not** claim that a metadata candidate is already a confirmatory Pilot task.

## Frozen observation window

- Window start: `2024-01-01`
- Registry freeze date: `2026-08-14`
- Contest timestamps are interpreted in UTC.
- Only `weekly-contest-N` contests whose contest start date is inside the window are considered.
- Biweekly contests are excluded from this task source.

## Metadata source and evidence boundary

The frozen discovery source is the public `doocs/leetcode` repository at revision:

`9f7e84b19e5326cb542e6238ac76e86bab438f0b`

The source is a **third-party mirror**. Its contest metadata and problem README front matter are used only to build the metadata candidate universe. They are not represented as first-party LeetCode evidence.

For each candidate DACDM retains the official LeetCode problem and contest URLs so later verification can be performed against public/first-party evidence where technically available.

DACDM does not commit the mirrored problem statements in this freeze. The generated registry stores metadata only: contest number/timestamp, problem slug, frontend ID, title, mirror difficulty label, source paths, URLs, hashes, and audit status.

## Candidate construction

A metadata candidate must satisfy all of the following:

1. Belong to a Weekly Contest in the frozen observation window.
2. Appear in the frozen contest metadata source.
3. Have a matching frozen problem metadata record.
4. Be labeled `Hard` in that frozen metadata record.

Canonical task ID:

`leetcode:weekly:<contest_number>:<problem_slug>`

Every candidate also receives:

`SHA256(canonical_task_id)`

The SHA-256 value is retained to support IF-02 deterministic resource-cap selection if a cap later becomes necessary. S1.3.7 itself applies **no resource cap** and keeps all metadata Hard candidates.

## Contamination audit

Each candidate is compared with every currently verified model training-cutoff record. Month-precision cutoff evidence remains month precision:

- release before cutoff month -> `EXCLUDED`
- release after cutoff month -> `ELIGIBLE`
- release inside the cutoff month -> `INDETERMINATE`

No exact cutoff day is invented.

For the current-model global status, a candidate is `EXCLUDED` if any currently registered model excludes it, matching the frozen protocol wording that a task is excluded when it predates the training cutoff of any model used in the test window. An indeterminate model result prevents a global clean classification.

This global status is an audit of the **current verified model registry**, not a permanent statement about a future expanded model registry.

## IF-09 gate

Every S1.3.7 candidate is frozen with:

- `oracle_status = PENDING_IF09`
- `confirmatory_task_status = NOT_ADMITTED_ORACLE_PENDING`

IF-09 later requires a sufficient executable test oracle: at least 20 distinct ordinary/edge tests or a complete authoritative test set, with 100% required for an individual solution to pass the registered oracle. Until that gate is satisfied, the metadata candidate is not admitted to confirmatory inference.

## K4 denominator sensitivity

S1.3.7 generates `k4_denominator_sensitivity.json` because S1.3.6 showed complete contamination exclusion of the current HumanEval and MBPP static registries against the four presently verified model cutoffs.

The sensitivity file is deliberately labeled:

`INTERPRETATION_SENSITIVITY_ONLY_NOT_FORMAL_K4_DECISION`

It reports:

- a denominator using the 1,138 static HumanEval/MBPP entries plus frozen LeetCode Hard metadata candidates; and
- an intentionally generous upper bound using **all** Weekly Contest problems in the frozen window as if every one were clean.

Neither is a formal K4 decision. The frozen protocol does not fully resolve the K4 denominator ambiguity, and metadata candidates remain unadmitted until IF-09.
