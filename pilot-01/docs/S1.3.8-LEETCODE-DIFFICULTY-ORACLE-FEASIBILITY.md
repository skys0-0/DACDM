# S1.3.8 — LeetCode Difficulty Evidence + IF-09 Oracle Feasibility

**Status:** IMPLEMENTED / PRE-INFERENCE GATE  
**Date:** 2026-08-14  
**Branch:** `s1-task-evidence-registries`  
**Depends on:** S1.3.7 frozen Weekly Contest Hard metadata candidate universe  
**Governing rules:** Frozen Protocol v1.0; Implementation Freeze IF-02 and IF-09

## 1. Purpose

S1.3.7 intentionally froze a metadata candidate universe without treating the third-party mirror difficulty label as confirmatory first-party evidence and without constructing an executable LeetCode oracle.

S1.3.8 closes the first of those gaps and audits the second without inspecting model results or making paid model calls.

It has two gates:

1. verify each candidate's current difficulty against LeetCode first-party metadata;
2. determine whether the repository currently possesses an IF-09-compliant executable oracle.

No task becomes confirmatory-admissible merely because its public problem statement contains examples.

## 2. First-party difficulty evidence

The one-time freeze first attempts the official LeetCode problemset metadata endpoint:

`https://leetcode.com/api/problems/all/`

For a candidate absent from that response, the collector falls back to LeetCode's official GraphQL endpoint:

`https://leetcode.com/graphql`

Only minimal metadata are retained:

- problem slug;
- frontend question ID;
- title;
- difficulty;
- official problem URL;
- source method and locator;
- retrieval timestamp.

The project does not copy LeetCode problem statements into the DACDM repository for this evidence step.

A difficulty evidence record is `SUPPORTED` only when:

- the official slug matches the frozen candidate slug;
- the official difficulty is `Hard`;
- when both sides expose a frontend question ID, the IDs match.

A mismatch is `CONFLICTING` and blocks admission.

## 3. IF-09 oracle feasibility rule

IF-09 requires at least 20 distinct deterministic executable cases, or a complete authoritative oracle, plus ordinary/boundary coverage where applicable. A task solution must pass 100% of the registered executable cases.

S1.3.8 does **not** manufacture hidden tests, scrape private judge data, or treat statement examples as an executable hidden oracle.

For audit visibility it counts public example Input/Output pairs in the frozen S1.3.7 mirror representation, but records:

`registered_executable_test_count = 0`

until a separate registered harness actually exists.

Therefore, absent a complete authoritative reproducible oracle, the current public-evidence path is classified:

`TEST_ORACLE_INSUFFICIENT_CURRENT_FROZEN_EVIDENCE`

This does not permanently exclude a candidate before an oracle-construction attempt. It means the task is not yet confirmatory-admissible and must remain blocked until S1.3.9 constructs and freezes an IF-09-compliant registered oracle or records a final insufficiency decision before model outcomes are inspected.

## 4. Admission state machine

For every S1.3.7 candidate:

1. first-party difficulty must be `SUPPORTED`;
2. current frozen contamination status must be `ELIGIBLE`;
3. IF-09 oracle must be `IF09_ORACLE_READY`;
4. only then may status become `CONFIRMATORY_ADMISSIBLE_PRE_INFERENCE`.

Otherwise the task remains blocked with an explicit reason.

No model performance result is consulted by this gate.

## 5. Outputs

The freeze writes:

- `registries/leetcode_official_problem_metadata.json`
- `registries/leetcode_difficulty_evidence.json`
- `backtest/s1_3_8/task_admission_readiness.json`
- `backtest/s1_3_8/summary.json`
- `backtest/s1_3_8/k4_denominator_gate.json`

All generated records carry the S1.3.8 phase label.

## 6. K4 denominator ambiguity

S1.3.7 showed that some plausible denominator interpretations produce a very high excluded fraction, but the frozen Protocol does not unambiguously specify the K4 denominator once heterogeneous benchmark sources and not-yet-admitted LeetCode candidates are combined.

S1.3.8 therefore **does not** make a formal K4 decision.

The gate file records:

`K4_DENOMINATOR_INTERPRETATION_UNRESOLVED_NO_FORMAL_K4_DECISION`

A denominator interpretation must be frozen before formal K4 evaluation and before model outcomes can influence that choice. The frozen 30% K4 threshold itself is not changed.
