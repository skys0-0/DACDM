# S1.3.9 — Registered LeetCode Oracle Construction

**Status:** PRE-INFERENCE / NO PAID MODEL CALLS  
**Phase label:** `S1.3.9_REGISTERED_ORACLE_CONSTRUCTION`  
**Governing rule:** IF-09 in `DACDM_Pilot_01_Implementation_Freeze_v1.0.md`

## Objective

S1.3.9 attempts to turn the S1.3.8 LeetCode Hard readiness queue into reproducible registered test-suite sources without inspecting model performance.

The frozen IF-09 minimum remains unchanged:

- at least 20 distinct deterministic executable test cases, or a complete authoritative test set;
- ordinary-case coverage;
- boundary/edge-case coverage where applicable;
- task pass requires 100% of the registered executable tests to pass.

## Frozen external source

Primary source for this phase:

- repository: `newfacade/LeetCodeDataset`;
- revision: `182cd19fd53161efd70a1ef074fe1056b659bfa3`;
- dataset version: `v0.3.1`;
- license in the frozen GitHub revision: MIT;
- paper: `arXiv:2504.14655`.

The source repository documents `input_output` test cases, an evaluation harness, canonical-solution verification, and generated test-case construction. The associated paper describes the dataset as containing 100+ test cases per problem over broad Python LeetCode coverage.

This is **not** treated as LeetCode's authoritative hidden judge data. It is an independent generated evaluation source.

## Registration rule

For each S1.3.7 candidate, S1.3.9:

1. preserves the S1.3.8 first-party difficulty decision;
2. preserves the frozen contamination decision;
3. joins the candidate to the exact frozen external dataset by normalized problem slug;
4. requires external difficulty `Hard`;
5. requires every `input_output` entry to be parseable as a deterministic input/output pair;
6. deduplicates cases by canonical JSON SHA-256;
7. requires at least 20 distinct pairs;
8. stores source revision, source file SHA-256, source row SHA-256, test-suite SHA-256, entry point, split, and count;
9. does **not** copy the test payload into the DACDM repository.

A source suite meeting the numeric threshold receives:

`REGISTERED_SOURCE_SUITE_EDGE_REVIEW_REQUIRED`

and is recorded in `registries/leetcode_oracle_registry.json`.

## Why registration is not final admission

The external dataset does not provide a frozen per-task label proving that a particular registered case is an ordinary case and another is a boundary/edge case under DACDM's IF-09 wording. S1.3.9 therefore does not infer edge coverage from serialized input size, random variation, or other heuristic proxies.

Likewise, this phase does not execute third-party test harness code directly in the repository CI. Executable-harness validation is deliberately separated so that untrusted external code is not silently executed during source registration.

Therefore even a numerically sufficient source suite remains:

- `ordinary_case_evidence_status = REVIEW_REQUIRED`;
- `edge_case_evidence_status = REVIEW_REQUIRED`;
- `executable_harness_validation_status = PENDING_SANDBOX_VALIDATION`;
- `confirmatory_admitted = false`.

## Scientific boundaries

S1.3.9 does not:

- change IF-09;
- change contamination rules;
- change the 60% aggregate LeetCode-hard threshold;
- choose tasks based on model performance;
- inspect model results;
- call paid model APIs;
- claim that generated tests are LeetCode hidden tests;
- formally evaluate K4.

## Exit and next gate

S1.3.9 exits when deterministic source coverage is frozen and every candidate has an explicit source-registration status.

The next gate is:

**S1.3.10 — Edge-Case Evidence and Executable Harness Validation**

Only after both ordinary/edge evidence and sandboxed executable-harness validation pass can a numerically sufficient registered source suite become IF-09 ready for confirmatory admission.
